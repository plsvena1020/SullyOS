# 小手机活化体系（Presence Layer）· 全功能架构分析

> 状态：v1.0 定稿（2026-09-15）。
> 定位：**总图**。回答"每个功能在活化体系下变成什么样"。
> 配套施工图：`docs/superpowers/plans/2026-09-15-airp-runtime-plan.md`（v1.2，脊柱+导演闭环的可执行计划，本图的 P0/P5 载体）。
> 命名：概念名「活化体系 / 临场层（Ambient Presence）」——恰好呼应现行 `APP_VERSION` 的代号 `Ambient Presence`；代码命名空间沿用 `utils/airp/`，不再另起。
> 原则：**不把 UI agent 化**。活化的是角色生活的"底座"，UI 表层该是确定性代码的地方保持确定性。

---

## 一、总纲：三层结构

现状的问题不是功能太少，而是**每个功能各自为角色"临时编造生活"**：聊天临时编情绪、朋友圈临时编动态、查手机临时编记录、主动消息按闹钟发。活化体系 = 把"角色的生活"从各功能里抽出来变成**唯一一份共享底座**，所有功能变成这份底座的不同投影。

```text
┌─────────────────────────────────────────────────────┐
│ L2 投射层（每个 App 是一个投影仪）                      │
│ 聊天 主动消息 朋友圈 日记 查手机 见面 通话 群聊 世界演绎 … │
└──────────────────────▲──────────────────────────────┘
                       │ 只消费，不另行编造
┌──────────────────────┴──────────────────────────────┐
│ L1 决策层（四个"脑子"，共享同一份底座）                  │
│ 导演（聊天轮规划） 生活模拟器（离线过日子）               │
│ 动机引擎（要不要主动联系） 管家（系统操作）               │
└──────────────────────▲──────────────────────────────┘
                       │ 读写都经权限门 + 审计
┌──────────────────────┴──────────────────────────────┐
│ L0 脊柱（六件套，全系统唯一）                            │
│ 能力注册表 / 世界事实库 / 事件流 / 权限分级 / 审计账 /     │
│ 生活状态机（日程·地点·精力·情绪·目标）                    │
└─────────────────────────────────────────────────────┘
```

三条铁律：

1. **一个事件只生成一次**：生活事实只在 L0/L1 产生，L2 各 App 呈现同一事实，不各自编造。
2. **确定性注入优先于模型判断**：每轮都在场的（记忆基线、时间、当前天气、日程）确定性注入，查询空间无限的才走工具（AIRP 计划 D1）。
3. **每个自主动作可审计**：任何 L1 决策落地前过权限门，落地后进审计账。

## 三、L1 决策层：四个脑子

### 3.1 导演（已设计，AIRP 计划主体）

每轮聊天前的规划脑：读快照→决定透露什么/推进什么/禁止什么→输出演出指令→角色模型表演→事实提交。详见 AIRP v1.2，此处不重复。

### 3.2 生活模拟器（P1，autonomy-round 蓝本扩展）

角色离线时的"过日子脑"。核心升级：把日程从**提示词风味文本**变成**可执行状态**。

```text
每一唤醒：
读日程与生活状态 → 推进当前活动（含计划偏离：加班/下雨改道）
→ 触发概率事件（同事约饭/看到甜品店）→ 产生 movement/activity/social_trace 事件
→ NPC 互动（复用 relationshipChat 引擎，产物留事件）
→ 更新精力情绪 → 计算下次唤醒锚点 → 判断是否产生"想告诉用户"的动机
```

驱动力分三种：**日程锚**（下班/到家）、**事件锚**（天气突变/剧情钩子到期）、**社交锚**（NPC 找她）。没有动机就沉默——安静的日常本身就是真实感。

### 3.3 动机引擎（P3）

主动消息从"定时闹钟"改为"动机驱动"。现状 selfSchedule 工具链完备，缺的是动机来源：

- 生活模拟器产出事件时标注 `wantToShare` 强度（思念/有趣/紧急）
- 导演在聊天轮也可以留下"下次想聊"钩子（`unresolvedThreads` 的反向用途）
- 动机≤阈值 → 攒着，下次用户在线时由导演决定是否自然提起（转述路径，autonomy 计划已设计）；>阈值 → 走现有主动消息管线发出，且推送内容有真实出处事件背书
- 现有防打扰闸（`amsg2ExpireGuard`）原样保留

### 3.4 管家（P7）

系统操作脑，`[[ACTION:*]]` 先例的注册表化。用户说"帮我把查手机图标藏起来"→ 管家解析为 `app_visibility` 能力调用 → 过 `confirm` 门 → 执行 → 审计。能力面：App 显隐、设置分项读写、通知整理、按语境的功能推荐。**不做**自由操作系统的口子——能力表外的请求一律"我做不到这个"。

## 四、L2 逐功能分析（核心章节）

格式：现状 → 活化形态 → 接口（消费/供给）→ 工程量 → 位次。
工程量：▲小（接线级） ▲▲中（1-2 个文件实质改造） ▲▲▲大（核心机制重构）。

### 4.1 聊天 Chat

- **现状**：`useChatAI` 工具循环 + `injectMemoryPalace` + 情绪 buff；全部职责压一次生成（用户本轮抱怨的"大量提示词搞乱"主战场）。
- **活化形态**：导演每轮规划（AIRP 阶段一）；事实提交进事件流（阶段二）。聊天从"角色的大脑"降格为"角色的嘴"——这是刻意的设计：嘴可以换模型，大脑只有一份。
- **接口**：消费=快照+演出指令；供给=正式对话事件（`conversation` 类，`confirmed_scene` 权威的主要来源）。
- **工程量**：▲▲▲（AIRP 计划已覆盖）  **位次：P0**

### 4.2 主动消息 Proactive（amsg2）

- **现状**：排程任务+fire_pack+self_log；发不发由排程决定，动机是隐式的。
- **活化形态**：动机引擎（3.3）接管"要不要发"，现有管线接管"怎么发"。P1 生活模拟器先产出带 `wantToShare` 的事件，P3 接动机引擎。fire 链路（工具循环/串行/凭据/推送）一行不动。
- **接口**：消费=事件流的 `wantToShare`+静默段+防打扰闸；供给=发出的消息本身也是事件（影响关系与记忆）。
- **工程量**：▲▲  **位次：P3**

### 4.3 查手机 CheckPhone

- **现状**：`phoneState`（浏览/消费/通话记录）**打开 App 时临时生成**；通讯录有 `note`（事实）vs `learned`（传闻）双措辞；真角色可双向对话（`relationshipChat`）；`aiAgent` 模拟痕迹。
- **活化形态**：全部痕迹改为**事件流的投影**。致命吸引力在这里：你查到她搜过的餐厅、和同事的聊天、昨天的打车记录，都是她"真的做过"的事——有事件 id 背书，不是查的瞬间编的。时机错位也顺带解决：她上午搜的餐厅，你下午查手机才看到，时间线是实打实的。
- **具体接线**：浏览记录←角色研究型事件（约会前查餐厅=导演/模拟器的 amap_search_places 调用记录）；消费记录←`activity` 事件（她真买了奶茶）；sim 记录←`social_trace`；通讯录 NPC 对话←模拟器离线时用 `runNpcConversation` 预生成的对话事件（不再是查手机瞬间跑双 LLM）。
- **改造注意**：`CheckPhone.tsx` 324KB 是全仓最大 UI 文件之一，只动数据源与生成入口（`handleGenerate*` 家族），不动 UI 结构；`allowFictionalContacts` 虚构 NPC 约束原样保留。
- **接口**：消费=`social_trace`/`activity`/`movement` 事件+知识边界（她不知道你看过她手机）；供给=查手机行为本身可留"她若知道会怎样"的 latent 事件（P5 后评估）。
- **工程量**：▲▲  **位次：P2（与朋友圈/日记同批，事件流首批投影）**

### 4.4 朋友圈 Moments（SocialApp）

- **现状**：打开时生成动态内容，`social_posts` store，豆瓣源做生态填充。
- **活化形态**：发帖行为由模拟器决定（不是每个事件都发——`wantToShare` 的公开档），**选择性披露**是核心规则：朋友圈是"她愿意展示的人设"，`hiddenEmotion` 与私密事件（`disclosedToUser=false`）绝不进正文。三天攒一个事件，发帖挑最有展示价值的那条，配图来自事件地点。
- **接口**：消费=`activity`/`movement` 事件+披露规则；供给=发出的动态本身是 `social_trace` 事件（查手机能看到她发了什么）。
- **工程量**：▲▲  **位次：P2**

### 4.5 日记 Journal

- **现状**：交换日记（`JournalApp.tsx:483`）+归档总结（`:594`）；写入走 `saveDiary`（`db.ts:1780`）。
- **活化形态**：事件的**私密反叙事**。和朋友圈是同一事实的相反投影：朋友圈写"今日份治愈"，日记写没说出口的犹豫。数据源=当天事件 + 导演 `beats.hiddenEmotion`（AIRP 导演输出里这个字段本来就是为此设计的）+ 情绪基调。夜间批生成（自主合光灯，autonomy 计划的 night 模板），走正常记忆水位——日记本来就是记忆形成路径，这条路不动。
- **接口**：消费=事件流+`hiddenEmotion`+情绪基调；供给=日记条目（可被记忆提取管线消化，现状已有）。
- **工程量**：▲  **位次：P2（三投影里最轻，可作为投影批的第一个试点）**

### 4.6 见面 DateApp

- **现状**：OBSERVE 观测协议完善（提示词注入/两层容错/HUD），地点时间感知已有。
- **活化形态**：导演在见面轮提供**场景约束块**（她刚下班赶来/外面在下雨/附近有她上周搜过的店——那条搜索记录是真的，来自事件流）；到场合理性由 amap 路线耗时约束（迟到要算得出来）；OBSERVE HUD 继续干观测的活，吃的还是同一份事实底座。**不接管正文生成**——见面的临场感正文仍归角色模型。
- **接口**：消费=事件流（movement/amap 调用史）+快照 scene；供给=`conversation` 类事件（见面对话权重高于线上闲聊，写入记忆时应受优待——现状 callPostFlow 已有先例）。
- **工程量**：▲▲  **位次：P5**

### 4.7 通话 CallApp

- **现状**：正文驱动 thinking→speaking + TTS 闭环，明确不接云端；已有 `callPostFlow` 挂入记忆。
- **活化形态**：只加两件事——**接听决策**（模拟器状态：开会中→"不方便，晚点打给你"；睡觉中→不接/静默）与**环境语境**（通勤中→背景嘈杂、说话短促）。正文、TTS、不接云端的边界全部不动。
- **接口**：消费=生活状态机（活动/环境）；供给=通话事件（callPostFlow 现有落点直接对上事件流）。
- **工程量**：▲  **位次：P5**

### 4.8 日程 Schedule

- **现状**：`generateDailyScheduleForChar` 生成风味文本注入提示词；节假日覆盖（`scheduleHolidaySync`）；角色可自管排程。
- **活化形态**：**生活模拟器的骨架本体**。日程从"注入的描述"升格为"可执行状态机"：每个 slot 是意图，模拟器推进时确认/偏离（加班=偏离事件），偏离本身是事件（"今天又拖到九点"成为她抱怨的料）。`[[ACTION:ADD_EVENT]]` 写入的用户日程是 `user_canon` 权威——模拟器即使在 L2 也不能无故抢掉用户指定的时间。
- **接口**：消费=节日覆盖+用户日程（canon）；供给=`activity`/`schedule` 事件+模拟器的推进轨道。
- **工程量**：▲▲（模拟器本体在 P1，这里只是被其消化）  **位次：P1（核心）**

### 4.9 记忆宫殿 Memory Palace

- **现状**：召回/提取/门牌/水位/认知消化，已经是全项目最成熟的子系统。
- **活化形态**：**几乎不动**。定位说清即可：记忆宫殿=她主观记得的；事实库=客观发生的；知识边界负责"她知道什么"，`misunderstood` 状态就是"她记错了"的形式化。三个衔接点：快照基线3（D1，每轮预取，不改管线）；离线经历经转述自然进提取（autonomy 蓝本原设计）；`confirmed_scene` 事实与记忆冲突时，记忆条目标记失效（阶段二已定义，保留修改记录）。
- **工程量**：▲（衔接触点均已在 AIRP 计划内）  **位次：P0（被动衔接）/ P2（冲突标记）**

### 4.10 情绪 Emotion

- **现状**：每轮 emotionEval 打分注入 buff（双开关门控）。
- **活化形态**：基调连续化。生活状态机持有**基线情绪**（今天的连续状态，跨轮跨天），emotionEval 从"当前情绪的唯一来源"降为"聊天后的修正信号"——聊开心了基线上调，被冷落了下调，过夜按事件翻篇。autonomy 计划延后项"情绪快照烤进 fire_pack"就是这个衔接点的近亲。
- **接口**：消费=事件流（好事件/坏事件量化影响基线）；供给=快照 `scene.mood` + 朋友圈/日记的情绪着色。
- **工程量**：▲▲  **位次：P1 末尾（模拟器稳定后）**

### 4.11 XHS（小红书）

- **现状**：搜索/浏览/详情工具链完整（`agenticTools` 内），`xhs_owned_posts`。她的 XHS 行为可以来自导演工具调用，但 owned posts 目前是孤立生成。
- **活化形态**：owned posts 并入发帖披露规则（与朋友圈同引擎不同平台——人设可以不同：朋友圈熟人面孔，XHS 兴趣面孔）；浏览/搜索行为事件化（查手机能看见她刷了什么）。
- **工程量**：▲  **位次：P2 尾（蹭朋友圈的发帖引擎）**

### 4.12 位置 Location

- **现状**：`char.location` 静态字段+`enrichMoveToPlace` 动作+高德代理；跨城靠剧情手动。
- **活化形态**：语义位置状态机（家→通勤→公司→午休→…），位置变化是 `movement` 事件，耗时受 amap 路线约束（"从公司到家 20 分钟"不再靠模型自觉）；节假日/出差的跨城= `user_canon` 允许下的多日 `movement` 弧，时区随城切换（复用 `resolveCharTimeZone`，不新造）。
- **接口**：消费=日程+amap；供给=事件流的`movement`+见面场景的真实感。
- **工程量**：▲▲  **位次：P1（模拟器的一部分）**

### 4.13 群聊 GroupChat

- **现状**：已有第二套导演（`groupChat/prompts.ts:178`）+timeline。
- **活化形态**：并入通用导演协议——同一个快照，按角色知识边界隔离（A 知道的事 B 不一定知道，`AirpKnowledge` 就是为此设计的）。多人场景的相关事实切分是导演的事，不是各角色模型自己的事。
- **工程量**：▲▲  **位次：P6**

### 4.14 世界演绎 worldHome

- **现状**：episodes/threads/chapters 完备（`engine.ts:292`），自带调度器。
- **活化形态**：episodes/threads 保留叙事管理职责，但**底层数据源切换成事件流**：一个 episode = 一段事件的叙事打包；`unresolvedThreads`（快照字段的同名概念）与 chapters 的开合判定共享。避免两套"世界状态"并存漂移——这是统一到"事件流是唯一事实源"铁律的最重要一次执行。
- **工程量**：▲▲▲（数据源迁移要小心 episode 兼容）  **位次：P6（与群聊同批）**

### 4.15 VR 小小窝 / 彼方 / 520

- **现状**：独立房间式虚拟空间（Q 版形象见 chibi 文档，彼方有漂流瓶后端）。
- **活化形态**：保持为**空间型投影**。小小窝的家具摆放、彼方的诗、520 的纪念，都是角色主动行为→事件→空间呈现。不追求实时联动（彼方的跨实例合写诗协议原样保留），只在"她为什么今天在彼方写了这首诗"背后有事件出处。**不动三处 Q 版形象管线**（chibi 契约）。
- **工程量**：▲（只加事件出处）  **位次：P8 尾（锦上添花）**

### 4.16 点餐（麦当劳/瑞幸）

- **现状**：聊天内 propose 循环完整（`useChatAI.ts:1432-1646`）。
- **活化形态**：只加一件事——订单成为 `activity` 事件（她请你喝的瑞幸进了查手机的消费记录）。propose 循环本身不动。
- **工程量**：▲  **位次：P2 尾**

### 4.17 番茄钟 Pomodoro

- **现状**：独立手绘风计时器（设计系统唯一例外风格，不外借）。
- **活化形态**：**反向活化**——它不是角色的事，是**用户状态的传感器**：你专注中 → 导演知道（回复变短/慢）、动机引擎压低主动消息优先级、她甚至可以"陪你安静"。番茄钟本体（计时/UI/style 隔离）一行不动。
- **工程量**：▲  **位次：P5 尾（一个衔接点，试起来很讨喜）**

### 4.18 蓝牙 Bluetooth

- **现状**：BLE 引擎+角色感知已有（见 bluetooth 文档）。
- **活化形态**：设备在场=空间临场感信号（你的耳机在旁边→她知道你大概在桌前）。已有角色感知逻辑，只需把感知结果接进快照 `scene`。
- **工程量**：▲  **位次：P8**

### 4.19 终端 / MCP / 代理基建

- **现状**：终端三 Tab+MCP 客户端+两条代理，与角色聊天零耦合（文档明示）。
- **活化形态**：**不动**。它们是工具提供方（能力注册表的 `mcp_passthrough` 消费者）和运维通道，属于 L0 之下的基础设施。刻意保持零耦合。

### 4.20 设置 / 统计

- **现状**：设置承载各功能开关（散布三处）；统计面板按 `APP_VERSION` 切分。
- **活化形态**：设置=管家的操作面板+`AirpPanel`（AIRP 阶段五）+审计中心+任务中心（fireKinds 用户可见化：进行中/可取消/重试）；统计新增"活化体检"面板：日均事件数、导演降级率、token 花费、自主行为时间线——版本标签天然适合按 AIRP 上线前后对比效果。
- **工程量**：▲▲（面板逐个做）  **位次：P7**

### 4.21 桌面与 App 管理（constants.tsx）

- **现状**：`INSTALLED_APPS`/`HIDDEN_APP_NAMES`/`DOCK_APPS` 静态常量。
- **活化形态**：仅把"改这些常量"注册成管家能力（`app_visibility`，confirm 档）——**不把清单本身动态化**。静态数组仍是唯一真源，管家只是多一个受审计的写入口。

## 六、不动的部分（防过度活化清单）

1. **聊天正文/见面正文/通话正文**：永远是角色模型的人格化表演，导演只给约束。
2. **番茄钟计时器与手绘风格**：设计系统例外风格不外借。
3. **终端/MCP/代理基建**：零角色耦合保持。
4. **彼方跨实例协议、chibi 三处形象管线、捏人器 PSD 管线**：契约文件列明的边界不动。
5. **`INSTALLED_APPS` 静态真源**：不动态化，只加受审计的写入口。
6. **排序/防打扰/expire/凭据安全等既有护栏**：一律原样继承，活化体系在护栏之内活动。
7. **确定性 UI**（渲染/输入/通知投递）：agent 是底座不是表皮。

## 七、量化预期与诚实边界

**预期收益**（P0-P3 完成后）：
- 记忆错乱/事实打架：结构性消除主要来源（导演+事实权威+冲突标记）。
- 跨 App 矛盾（聊天公司/朋友圈商场）：消除——同一事实源。
- 主动消息"到点就发"感：消除——有动机有出处。
- 角色离线冻结感：大幅缓解——生活痕迹+转述。

**不会自动变好的**：
- 文笔与临场反应（取决于角色模型质量——所以 `directorModel` 可单独配）。
- 缺德的模型还是会偶尔违抗指令——导演降低频率，不归零。
- 事件密度设计不好会"太戏剧"——生活感来自惯性，参数要实测（快照事实上限/唤醒节奏均列入"实测回填"）。
